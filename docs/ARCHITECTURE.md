# ARCHITECTURE.md

ARSU is five cooperating subsystems. **All state flows through the
blackboard** — there is no agent-to-agent messaging and no hidden shared
memory. The dashboard is a read-only (plus chaos-inject) view of the same
board.

## Subsystems

### 1. Simulation (`packages/sim`)

The demo target: a fake-but-faithful airline operations estate modeled on
real outage post-mortems.

Services (the graph an ops org actually has):

| Service | Depends on | Real-world echo |
|---|---|---|
| `unimatic` | — | United's flight-info hub — the Aug 6 2025 SPOF |
| `unimatic-standby` | — | cold replica; failover target |
| `weight-balance` | `unimatic` | W&B calc died with Unimatic |
| `dispatch` | `unimatic`, `weight-balance`, `crew-sched`, `notam` | release authority — ground stop when down |
| `crew-sched` | `unimatic` | Southwest Dec 2022 meltdown |
| `pax-connect` | `unimatic` | bookings/check-in |
| `notam` | — | FAA NOTAM outage Jan 2023 |
| `ops-radar` | `unimatic` | position feed for the live map |

Health model: each service has intrinsic state (`up | degraded | down`) and
**effective state** computed recursively — a service is effectively down when
it is down or any required dep is effectively down. Cascades are the whole
point.

Behavioral coupling: `dispatch` down → flights can't depart (ground stop,
planes accumulate at gates); `unimatic`/`ops-radar` down → position feed goes
stale; `weight-balance` down → dispatch blocks releases.

Flight map: ~40 flights on real airport-pair great-circle routes (seed data
generated by `npm run seed`, `data/flights.seed.json`). Live positions tick
once per second over WS. Optional adapter lane can swap in live ADS-B
(airplanes.live / OpenSky) later — see SPEC §flight-data.

Control plane (what response agents act on): `POST /sim/action` —
`restart`, `failover`, `reroute`, `repair`. Chaos plane: `POST /sim/chaos` —
`kill`, `degrade`, `cut_dep`, `corrupt`. These are *separate* surfaces:
chaos is what the demo operator presses; action is what only agents may use.

### 2. Blackboard (`packages/core`)

Firestore-shaped store. Interface: `doc()`, `collection()`, `add()`,
`set/update`, `onSnapshot()` — implemented twice:

- `LocalBlackboard` — in-memory + JSON persistence (`data/blackboard.json`),
  event-emitter watchers. Default; zero credentials.
- `FirestoreBlackboard` — same interface on `@google-cloud/firestore`.
  Activated when `FIREBASE_*` env is present. **This is the Firebase
  qualification**: the board IS the product's nervous system.

Collections: `nodes`, `edges`, `invariants`, `specs`, `violations`, `tasks`,
`agents`, `events`, `skills`. Field schemas in SPEC.md.

### 3. Swarm (`packages/swarm`)

- `ModelProvider` — the single boundary for model calls
  (`complete()`, `planJSON()`). `GeminiProvider` (generativelanguage API,
  `GEMINI_API_KEY`, model from `GEMINI_MODEL`, default `gemini-2.5-flash`);
  `SimulatedProvider` (deterministic heuristic tables — same call sites, no
  network, labeled `SIM` everywhere in UI).
- `AgentRuntime` — spawn/heartbeat/task-claim loop. Agents claim `tasks`
  docs by CAS lease; roles filter which tasks they can claim.
- Roles:
  - `recon` — probe services (`/sim/registry` + op endpoints), author
    `nodes`/`edges` + confidence + evidence.
  - `verify` — author `invariants` + `specs` per node.
  - `proof-runner` — execute invariants on interval; failures mint
    `violations` + `events`.
  - `response` — claim `remediate` tasks, load the block's `skill`, execute
    steps against `/sim/action`, re-run the invariant, resolve or escalate.
- `Orchestrator` — boot sequence (seeds recon tasks on LAUNCH), violation
  triage (violation → task with skill hint + priority), escalation on
  repeated failure, mission-complete events.

With Gemini: recon/verify/orchestrator prompts produce the ontology fields,
invariant sets, and triage plans — model output lands directly on the board.

### 4. Server (`packages/server`)

One Node process hosts everything for the demo: mounts sim control/data
endpoints, owns the blackboard + runtime, exposes REST (`/api/state`,
`/api/launch`, `/api/chaos`, `/api/resolve`) and WS (`/ws` pushing `event`,
`invariant`, `flight`, `agent` messages). In production this splits to Cloud
Functions / Cloud Run; the blackboard switch is config, not code.

### 5. Control board (`apps/dashboard`)

React (Vite). Four live surfaces + one control strip:

- **MAP** — dark-tiled leaflet view: moving flights, airport nodes, service
  health badges, stale-feed indicator. The "whoa" surface.
- **ONTOLOGY** — d3-force graph of `nodes`/`edges`, colored by effective
  health; violations pulse.
- **INVARIANTS** — board of checks, green/amber/red, last-run, author agent.
- **SWARM** — agent cards: role, state, claimed task, decisions.
- **FEED** — the `events` stream: probes, proofs, violations, actions,
  resolutions. Timestamped, filterable.
- **CHAOS BAR** — the demo buttons: kill `unimatic`, degrade `weight-balance`,
  cut a dep, restore. Plus **LAUNCH SWARM** to start a mission.

Every surface subscribes to `/ws`; nothing polls.

## Data flow — one full mission

1. Operator presses LAUNCH → `tasks` seeded with recon jobs.
2. Recon agents probe → `nodes`, `edges` land → graph view blooms.
3. Verify agents author `invariants` + `specs` per node → board fills green.
4. Proof runner loops — steady green ticks in FEED.
5. Operator presses CHAOS: kill `unimatic` → cascade: `dispatch`, `w&b`,
   `crew`, `pax`, `ops-radar` effective-down → departures stop on the map.
6. Invariants fail → `violations` → orchestrator triages (SPOF detected:
   edges fan-in on `unimatic`) → `remediate` tasks per skill.
7. Response agents execute skill `hub-failover` (activate `unimatic-standby`)
   → health restored → proofs re-green → `events`: *resolved*.
8. Dashboard shows the whole arc end-to-end: map froze → red board → swarm
   worked → green.

## Plug paths (built, activated later)

| Slot | Default (now) | Production (when keys exist) |
|---|---|---|
| Model | `SimulatedProvider` | `GeminiProvider` via `GEMINI_API_KEY` |
| Blackboard | `LocalBlackboard` | `FirestoreBlackboard` via `FIREBASE_*` |
| Hosting | `vite dev` / static | Firebase Hosting |
| Identity | none | Firebase Auth on control board |
| Agent runtime | in-process | Cloud Run jobs / Functions |

## What ARSU deliberately is NOT (yet)

- Not full formal verification (TLA+/Coq). We ship *executable invariants*
  authored pre-incident — the honest, demoable core of the same idea, and the
  roadmap line judges ask about.
- Not pointed at a real company — the sim stands in; the swarm code targets
  generic probe/action surfaces so a real estate adapter is a lane, not a
  rewrite.
