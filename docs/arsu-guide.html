ARSU · Attack Response Swarm Unit

How a swarm maps, proves,
and repairs a system

A guided tour of the ontology, the three practice layers, the communication faults, and what "verified recovery" actually means.

Use ← → arrow keys, space, or the buttons below. ~5 minutes.

01 · The one rule

Agents never talk to each other.
They talk to the Blackboard.

Every agent reads work from the board and writes receipts back to it. No direct agent-to-agent messages, no hidden shared memory.

agent→ writes →blackboard→ read by →agent
Why it matters: everything the swarm believes is a record you can open — in the Blackboard view or the Pipeline walkthrough. That's the whole audit trail.
02 · The ontology

Four record types become the map

Nodes

Discovered systems. Each has health, receipts, provenance, and which agent found it.

Edges

Directed dependencies — "release-gate depends on message-consumer". This is the graph the orchestrator reasons over.

Specs

Human-readable contracts authored per system by verification agents through the ModelProvider.

Invariants

Executable checks derived from specs — the runner fires them on an interval and records pass/fail receipts.

Discovery writes nodes + edges. Verification agents write specs + invariants. The runner turns invariants into evidence.
03 · Three layers only

The practice environment, in one picture

Layer 1

Infrastructure

Modeled hosts: gateway, broker, consumer. The machines things run on.

Layer 2

Communications

publisher → broker → consumer. Educational message receipts you can open and inspect.

Layer 3

Operations

A release decision that can only act on messages it can trust.

The point of the demo: a host can be perfectly healthy while the data flowing through it is corrupted, replayed, missing, or stale. That's what the swarm is for.
04 · The message

What a communications envelope looks like

{
  "id": "notam-0007",
  "sequence": 7,
  "topic": "notam.runway",
  "publisher": "notam-source",
  "sentAt": "2026-11-22T14:02:11Z",
  "receivedAt": "2026-11-22T14:02:12Z",
  "payload": { "runway": "09L", "status": "CLOSED", "reason": "WIP" },
  "hash": "sha256:9c1f…",
  "freshnessMs": 1040
}

Modeled after the public FAA SWIM/JMS publish–broker–consume pattern. It's an educational receipt — not a real NOTAM, JMS, or ASTERIX implementation.

05 · The four faults

How communication breaks

payload-corruption

Body changes after publish. Hash mismatch proves tampering, not a network hiccup.

sequence-gap

A delivery never arrives. The consumer sees sequence jump 7 → 9.

message-replay

An old envelope comes back as new. Duplicate sequence exposes it.

stale-message

Traffic flows, but it's too old to act on. FreshnessMs blows the budget.

Each fault is injected into the simulation only — and each has a check that watches for exactly that failure shape.
06 · Detection

Invariants fire, violations open

runner executes check→FAIL→violation opens→orchestrator triages

The proof runner runs every invariant on its interval and writes receipts. A fail doesn't just turn a dot red — it opens a violation record with the check, the node, and the failing detail.

The orchestrator's job: separate the root failure from collateral effects. A broken link fails the consumer AND everything downstream — only the root gets a remediation task.
07 · Response

Tasks dispatch to skills

triage→remediation task→response agent claims it→skill executes

Response units claim tasks through the board and run a skill — for the comms slice that's things like reconnect-subscription or purge-stale-queue. Every step lands as an event receipt.

You can watch this live in the Swarm view — the incident trace lights up DETECTION → TRIAGE → DISPATCH → RESPONSE → RESOLVED.
08 · Verification

"Recovered" means the checks say so

A scenario only closes when every covered check passes again after the response — not when a banner turns green, not when the agent says it's done.

Verified recovery = fault detected + response executed + fresh pass on all 34 checks + evidence JSON you can download.
Honest limit: verification proves the covered checks passed. It can't claim universal correctness beyond them. The UI says exactly this.
09 · Provenance

What's real and what's modeled

Simulated

The 8-component estate, traffic, faults, and agent behavior in SIM mode.

Public reference

FAA SWIM/JMS distribution concepts and EUROCONTROL ASTERIX as format inspiration — cited, never claimed as implementation.

ModelProvider

GEMINI_API_KEY flips contract authoring and triage reasoning to Gemini. SIM is the deterministic default.

Firestore

Optional persistence for the Blackboard via Firebase env vars — otherwise local-only.

Nothing implies access to real FAA, ADS-B, or private aviation networks. Live data only appears when you wire it.
10 · Try it

The 60-second demo loop

  • Launch — Swarm view → Launch environment. Watch 8 systems, 7 links, 34 checks get authored.
  • Map — Pipeline view walks each stage: discovery → ontology → contracts → detection → triage → skills → outcome, with the raw board record under every claim.
  • Break it — Change a message payload. The trace lights up and a violation opens.
  • Watch it heal — response executes, all 34 checks pass again, outcome marked VERIFIED.
  • Keep the receipt — Download evidence JSON on the recorded run.
Run it: npm run dev:practice → open the printed URL. Ephemeral board, nothing saved is touched.
